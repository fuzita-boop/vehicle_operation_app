# 検証記録

## 開発プレビューでの確認

静的Viteプレビューでホーム画面を表示し、認証画面やサーバーAPIへの遷移が発生しないことを確認しました。ホーム画面からの日次記録・月次レポートのリンクは、ルート配下でそれぞれ`/daily-record`、`/monthly-report`になることを確認しています。

Service Workerは開発プレビューで有効になり、ルートをスコープとして登録されました。開発モードのWorkboxキャッシュには`/index.html`および`/registerSW.js`が確認されています。GitHub Pages向けの本番ビルドでは、Vite PWAの生成SWがJavaScript、CSS、HTML、Web App Manifest、アイコンを含む事前キャッシュ一覧を生成します。

GitHub Pagesのサブパス対応を確認する際は、ビルド生成物を公開先リポジトリ名のディレクトリ配下に配置した状態で検証します。通常のViteプレビューは生成物をルート配下に置くため、そのままではGitHub Pagesのサブパス構成を再現できません。

ローカル静的ホストではディレクトリURLに対して一覧画面を返す実装があるため、サブパス検証では`index.html`を明示した起動確認と、公開後のGitHub Pages URLでの最終確認を分けて実施します。

GitHub Pages相当の`/vehicle_operation_app/`配下にビルド成果物を配置した検証用ホストでは、ホーム画面の起動と、`/vehicle_operation_app/daily-record`への遷移を確認しました。リンクはサブパスを保持し、日次記録画面ではJST日付を初期値にした出発入力フォームが表示されました。

同じ検証ホストでは、Service Workerが`/vehicle_operation_app/`をスコープとして有効化され、事前キャッシュにHTML、JavaScript、CSS、Web App Manifest、アイコンが含まれることを確認しました。また、`/vehicle_operation_app/monthly-report`をURLから直接開いても、GitHub Pages用404復帰処理を経て月次レポート画面が表示されることを確認しました。

バックアップ復元の通し検証では、GitHub Pages相当のホーム画面から運転者情報の編集画面を開けることを確認しました。入力・保存後にブラウザのダウンロード機能を使ってJSONバックアップを取得し、端末内DBの初期化・復元を続けて検証します。

検証用の運転者名を画面から入力して保存したところ、「運転者名を端末に保存しました。」と表示され、ホーム画面の運転者情報カードにも保存値が表示されました。これにより、プロフィールのUI保存がIndexedDBへ反映されることを確認しました。

ホーム画面の「バックアップを保存」を押すと、`車両運行日報_バックアップ_2026-08-12.json`がブラウザのダウンロード履歴に生成されることを確認しました。

復元テストでは、ブラウザのIndexedDB削除APIを実行後にホーム画面を再読み込みしました。開いているアプリ接続の影響を受ける可能性があるため、実運用での初期化・復元確認は、別タブを閉じた状態で行う前提として扱います。

その後、検証用に`profile`、`cycles`、`records`の各ストアを明示的に初期化できることを確認しました。この初期化後にダウンロード済みJSONをUIから復元して、表示値が戻るかを検証します。

明示的なストア初期化後にホーム画面を再読み込みすると、運転者名が「未設定」に戻ることを確認しました。復元用のJSONファイル入力欄も検証環境で確認できています。

ダウンロード済みJSONを復元用入力欄から選択したところ、「バックアップを端末内データへ統合しました。」と表示され、運転者名「検証運転者」がホーム画面に復元されました。UI経由のバックアップ保存→IndexedDB初期化→復元→再表示の通し検証を完了しています。

検証用の静的Webサーバーを停止した後も、Service Workerのキャッシュを介してホーム画面を再起動し、日次記録画面へ遷移できることを確認しました。これは初回オンライン起動後のオフライン相当の起動・閲覧検証です。

同じ通信元停止状態で、日次記録フォームに出発時間・出発時走行距離を入力して保存したところ、「出発記録を端末に保存しました。」と表示され、一覧・サイクル集計に1件の記録が反映されました。オフライン相当での入力・保存も確認済みです。

GitHub Pagesの公開URL `https://fuzita-boop.github.io/vehicle_operation_app/` でホーム画面が正常に起動することを確認しました。続けて `/vehicle_operation_app/monthly-report` への遷移も成功し、公開環境でもサブパスのルーティング・月次レポート・A4印刷操作が利用可能です。

公開URLで`/vehicle_operation_app/monthly-report`を直接指定しても月次レポートが表示され、404復帰を含むサブパスルーティングが機能することを確認しました。また、公開環境ではService Workerが制御中であり、スコープ`/vehicle_operation_app/`のWorkbox事前キャッシュが作成されています。

Phase 40の操作フロー検証では、開発用PWAの日次記録画面で出発時刻・出発時走行距離を入力し、未完了状態の保存・帰着入力への遷移を確認する準備を完了しました。

出発記録の保存後、記録カードがオレンジ色の左ボーダー・「帰着未入力」バッジ・警告文・オレンジ色の「帰着」ボタンで表示されることを確認しました。「帰着」を押すと、出発情報を参照表示した帰着専用フォームが自動展開され、フォーム位置までスクロールすることも確認しました。

帰着情報（終了時間・終了時走行距離・稼働件数）を保存すると、未完了表示が消え、走行距離・稼働件数・集計値が更新されることを確認しました。通常の「帰着」ボタン経由では、保存後も日次記録画面に留まります。

ホーム画面からの帰着入力自動展開の検証用に、完了済み記録とは別に未完了の出発記録を作成しました。記録一覧とサイクル集計で「帰着未入力」1件としてオレンジ色に表示されています。

ホーム画面に帰着未入力バナーが表示され、そのリンクには対象記録IDを含む`openArrival`パラメータが付与されることを確認しました。バナーを押すと対象の帰着フォームが自動展開され、フォーム位置までスクロールして出発情報が表示されました。

ホーム経由で開いた帰着フォームを保存すると、対象記録の未完了状態が解消され、帰着未入力バナーが消えたホーム画面へ自動的に戻ることを確認しました。

Phase 41では、月次レポートを旧版に近い構成へ復元しました。開発画面で対象サイクル選択、前後ナビゲーション、中央タイトル、運転者・車両情報、7列の罫線付き一覧、2項目の集計、青い印刷ボタン・緑のPDF保存ボタン・ホームボタンを確認しました。印刷対象には7列テーブルがあり、ガソリン代欄は画面上では非表示でA4印刷時のみ表示されます。

Phase 42では、日次記録一覧を旧版に近いラベル付きカード形式へ復元しました。記録カードには日付・出発／終了時刻・出発／終了距離・走行距離・稼働件数を表示し、編集ボタンから記録日、出発／終了時刻、出発／終了距離、稼働件数を修正できることを画面上で確認しました。編集時には走行距離の再計算値と、保存・取消ボタンを表示します。

検証用記録の出発時間を編集・保存し、保存メッセージの表示後、編集モードが閉じ、一覧に変更後の時刻が直ちに反映されることを確認しました。

Phase 43では、通常記録を上段（日付・出発・終了）と下段（出発距離・終了距離・走行距離）の2段3列カードへ変更しました。画面上で3列グリッドと右側の編集・削除ボタンが存在することを確認しています。帰着未入力記録はオレンジの左枠、未入力表示、帰着ボタンで強調されます。
